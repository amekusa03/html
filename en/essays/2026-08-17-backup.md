# I created this story because the backup didn't finish.

A backup is a mysterious thing that makes you feel safe just by its existence, but it gets in the way when you start using it.

The beginning of the problem was simple: the standard backup app for the OS just wouldn't finish. No matter how many hours I wait, it doesn't complete. If you run it while doing normal work, it will completely take over the CPU and I/O, making your PC essentially unusable. However, it seems foolish to monopolize your PC just for backup. It didn't take long for me to decide that I should start making more.

![alt text](essays/2026-08-17-backup.png)

## Organize your requirements

It's fine if you decide to make one, but it's not a good idea to start writing blindly. First I thought about what I wanted.

- I want you to move while doing your normal work. In other words, I want it to stop automatically when the CPU or I/O load is high.
- Files are not compressed. There are two reasons: There is a risk that the contents will be destroyed if the compressed archive is corrupted, and it takes a certain amount of time to compress and expand.
- I want to use snapshot format instead. By using the hard link function of `rsync`, you can manage generations while saving disk space.
- I want it to run on time. However, I don't want to manage the daemon separately, so I want to complete the schedule processing within the app.

I have a vision of turning this into a GUI app.

## Technology selection

I chose Qt6 as the GUI framework (Qt5 is also supported) and C++17 as the language. Qt is still the most solid choice for writing Linux desktop applications.

I decided to leave the main body of the backup to `rsync`. `rsync` is dead and reliable, and if you use the `--link-dest` option, you can also perform snapshots neatly. Where there is no reason to reinvent the wheel, we do not hesitate to use existing tools.

Load monitoring reads `/proc` and periodically checks the CPU usage rate and I/O wait rate, and when the threshold is exceeded, `rsync` is paused, and when it drops, it is restarted. It's a lot of fun to implement this kind of behavior that "understands" things.

## Conclusion

Once created, the backup started to work silently and automatically. It stops when the load is high and restarts when it is free. There is no problem with normal work. I think the initial requirements were met.

I don't know if the idea of ​​``if you're not satisfied with a standard app, make one'' is the work of an engineer, but at least in this case, it was the right thing to do.
