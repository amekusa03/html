# The Evolution of Technology and the Impact of C++/CLI: The Journey from MS-C to the Latest C# (.NET 10)

2026-11-18

## Evolving Development Environments and “Intuitive Coding”

Recently, I updated my development environment from Visual Studio 2022 to 2026 and migrated the target framework from the previous .NET Framework 4.7 straight to the latest **.NET 10**.

What strikes me most when working with the latest version of C# is that **it has become “extremely intuitive and easy to write.”** With less boilerplate code and a more refined language specification, I can immerse myself in building the actual logic without my train of thought being interrupted. I can really feel the difference—development efficiency has taken a significant leap forward.

## From MS-C to MFC, and Then to Modern C#

Come to think of it, my journey into programming began back in the days of **MS-C (Microsoft C)**.

- **The MS-DOS Era**: Back when we were constantly battling the 640KB conventional memory limit, always keeping segments and offsets (the `near` and `far` pointers) in mind, and directly accessing VRAM and hardware interrupts.
- **The Windows/MFC Era**: Back when I wrote code believing that “C++ and MFC are the gold standard for Windows application development,” making full use of the document-view structures and message maps defined by `CWinApp`, `CDocument`, and `CView`.

That “sense of being directly connected to the hardware” from back then, along with the rigor of managing memory down to the single-byte level, has become an integral part of who I am as an engineer. However, viewed from the perspective of today’s **C# / .NET 10**—with its garbage collection (GC), sophisticated asynchronous processing, and robust ecosystem—it feels like a world apart, as if from a completely different era.

## The Shock I Felt Working with C++/CLI Again After So Long

Just as I was enjoying such a comfortable life with C#, I had the opportunity to work with **C++ (C++/CLI / .NET 7)** at work. That’s when I found myself smiling wryly at how I just couldn’t seem to make any progress.

The moment I opened the source code I had inherited, I was confronted with the stark reality of the “boundary between native C++ and .NET”—something you don’t have to worry about in modern C#.

### Considerations for `ref class` and `gcnew`

In C#, you simply declare it as ``class`` and instantiate it with ``new``, and then the garbage collector takes care of everything behind the scenes. However, that’s not the case with C++/CLI.

- **`ref class`**, which indicates that it is a managed class
- **`gcnew`**—Creates an object under the GC's control
- The standard **`new`** allocated on the traditional C++ native heap

"Is this instance managed or unmanaged?" "Is it a pointer tracking handle (`^`) or a raw pointer (`*`)?" “What is the memory lifecycle like?”—Even when dealing with just a single object, memory management constantly occupies a corner of your mind.

### Pointer Arithmetic That Iterates Through an Array Using `++`

What really made me almost gasp was the array scanning code.

In modern C#, you’d write this safely and intuitively using `foreach`, LINQ, or simple index access, but the code in front of me still retained **the good old-fashioned syntax of using pointer arithmetic to increment the array address by `++` as you move through it**.

The moment I saw it, I was overcome by a fierce wave of nostalgia mixed with a pleasant sense of anticipation—the thought, “Am I really going to safely examine and handle this in a modern work environment…?”—and I couldn’t help but let out a **“Oh…”**.

## Hidden Complexity and the Ingenuity of Our Forebears

Through this experience, I was reminded once again just how much complexity modern C# hides behind the scenes—and how it protects developers from pointless mistakes—even though we often take its benefits for granted.

| Comparison Criteria | Modern C# (.NET 10) | C++/CLI (.NET 7) |
| :--- | :--- | :--- |
| **Class Definition and Creation** | Unified using `class` / `new` | Mix of `ref class` / `gcnew` and native `new` |
| **Memory and References** | Automatically managed by the GC (usually no need to be aware of it) | Coexistence of managed handles (`^`) and raw pointers (`*`) |
| **Collection Operations** | Safe and intuitive with `foreach` and LINQ | Index traversal and pointer incrementation (`++`) |
| **Development Focus** | Allows you to focus on the essence of business logic | Requires constant awareness of memory space and boundary integrity |

Back in the days of MS-C and MFC, we handled these “considerations regarding pointers and memory” as naturally as breathing. Now that we’ve become completely accustomed to the highly polished C# environment, coming back to C++/CLI code after so long gave me a fresh sense of wonder, as if I’d just opened a time capsule.

It is precisely because I understand the gritty yet profound challenges of low-level programming that I deeply appreciate the advancements brought about by modern languages and frameworks. It was a moment when I was able to quietly reflect on my own journey as an engineer.
