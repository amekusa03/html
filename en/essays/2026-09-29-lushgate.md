# Automatic Irrigation System for Vegetable Gardens: Switching from Wi-Fi to BLE — Connecting from the Garden to Your Smartphone Without a Router

2026-09-29 / ESP32 / IoT / BLE

In my previous essay, I wrote about the process of “subtraction”—shifting from the “big guns” of solar power generation to a modest setup consisting of four AA batteries and two A batteries. Now that the hardware design has been finalized for the time being, the next challenge has loomed large.

"How to Change Settings on Your Smartphone"

The crux of the problem is simple. The garden is behind the house, and it’s doubtful whether the Wi-Fi router’s signal even reaches that far. Even if it does, when running the ESP32 in AP (access point) mode, I have to reconnect my smartphone to the ESP32’s SSID. Manually switching from your everyday Wi-Fi network and typing the IP address directly into the browser—that’s what makes it such a hassle. For a device that calls itself “IoT,” having to stare at the settings screen every time you connect is putting the cart before the horse.

## From Deep Sleep to Light Sleep: The First Major Change

As of September 22, the design called for putting the ESP32 into **Deep Sleep** between measurements. Deep Sleep is the deepest sleep mode, in which all RAM contents are discarded, leaving only the RTC memory intact. While it offers the best power efficiency, it has the characteristic that “waking up is equivalent to a reset.”

However, as we moved forward with implementation, we discovered some areas where it didn't work well with Deep Sleep.

Since waking up from Deep Sleep is equivalent to a reset, variables in RAM (such as cumulative rainfall values) are lost. Even if they are saved to the RTC slow memory (`RTC_DATA_ATTR`), the capacity is limited, and it’s too cramped to fit everything, including the configuration structure. Above all, the BLE stack (NimBLE), which will be discussed later, cannot coexist properly with Deep Sleep. Since BLE runs a large number of initialization processes upon startup, repeating the cycle of initialization → termination → initialization every three minutes causes processing time to balloon, making it impossible to achieve any power savings.

That’s why we adopted **Light Sleep**. The contents of RAM are preserved as-is, and the system wakes up instantly in response to a timer or GPIO interrupt. Although the current consumption is approximately **0.13 mA**—slightly higher than that of Deep Sleep (0.006 mA)—with intermittent operation in 3-minute cycles, the total daily current consumption increases only slightly. This is not enough to have a significant impact on battery life.

There is no longer any need to prefix state variables with `RTC_DATA_ATTR`; you can simply declare them as regular `static` variables. This makes the code much simpler.

## Discontinuation of Wi-Fi AP Mode and Full Transition to BLE

With the transition to Light Sleep, we also fundamentally reevaluated the communication protocol.

As of the September 23 commit (`feat: complete software implementation`), the Wi-Fi AP mode was still present. This is the traditional method where the ESP32 acts as an access point, and a smartphone connects to it to access `192.168.4.1`. The HTML for the settings screen was embedded in the firmware, and it was running a web server (`web_server.c`) and the Wi-Fi AP initialization (`wifi_ap.c`).

Then, on September 29, with a single commit labeled `feat: migrate to NimBLE Web Bluetooth`, this entire configuration was replaced.

Deleted files: `web_server.c`, `wifi_ap.c`, `web_server.h`, `wifi_ap.h`, and the HTML files for the built-in web pages.  
Added files: `ble_gatt.c`, `ble_gatt.h`, and `docs/index.html` (Web Bluetooth app on GitHub Pages).

I ditched the entire Wi-Fi stack and switched to **NimBLE** (a lightweight BLE stack built into the ESP-IDF). Communication with smartphones uses the **Web Bluetooth API**, allowing you to connect directly to BLE devices from your browser. There’s absolutely no need to change your smartphone’s Wi-Fi settings. No router is required either.

Here's how the process went.

1. Press the **BOOT button (GPIO9)** on the ESP32 (the LED will flash and advertising will begin)
2. Open `https://amekusa03.github.io/LushGate/` in your smartphone's browser
3. Tap “**Connect to LushGate**” → BLE connection established
4. Change watering schedules, rainfall thresholds, and pump duration; synchronize time; perform manual watering tests; view history

It's overwhelmingly easier than Wi-Fi. Best of all, by hosting the web app on GitHub Pages, I was able to eliminate HTML from the firmware. The firmware should only do what firmware is supposed to do.

## BLE GATT Design: Five Key Characteristics

The contents of `ble_gatt.c` consist of five characteristics defined as NimBLE GATT services.

| Characteristic | Function |
|---|---|
| `CONFIG` (0001) | Read/write settings; save to NVS |
| `TIMESYNC` (0002) | Write smartphone time to RTC in Epoch format |
| `PUMP_CMD` (0003) | Turn pump ON/OFF; specify duration in seconds |
| `STATUS` (0004) | JSON notifications for rainfall, pump status, and raw sensor values |
| `HISTORY` (0005) | Retrieve the last 60 watering records by specifying an index |

`STATUS` Characteristic supports Notify (push notifications), and while connected, sensor readings are sent in real time every second. Watching the voltage of the rain sensor fluctuate slightly on my smartphone screen while testing it by placing a drop of water on my fingertip—it was quite a fun experience.

## Dealing with the Double Watering Bug

Right after I finished implementing BLE, a pesky bug popped up.

"Immediately after the reset, the sprinkler system—which shouldn't be running—starts up."

When I dug deeper into the cause, this is what I found: There were situations where the firmware had difficulty distinguishing between waking up from Light Sleep and resetting after a power loss. Since the flag indicating “Watered Today” (`s_last_water_day`) is stored in RAM, it remains active after waking from Light Sleep; however, when a full reset occurs—such as during a battery replacement—the RAM is naturally cleared and the flag reverts to 0xFF. This should have been preventable by cross-checking with the previous watering time saved in NVS (non-volatile storage), but the restore process sequence was flawed, resulting in cases where the “20-hour guard” did not function.

In the commit labeled `fix: prevent multiple waterings using RTC slow memory and pre-watering state commit`, I added a sequence guarantee to write the “Today’s Watering Complete Flag” and the “Watering Time Epoch” to NVS **immediately before** watering begins. This ensures that even if a reset occurs during watering, the system can correctly determine upon the next startup that “Oh, watering has already been done today.”

Furthermore, in the `fix(firmware): Light Sleep復帰の安定化` commit on the same day, it was discovered that if `deinit` in NimBLE was not explicitly called when exiting BLE mode, the modem and Light Sleep would conflict, causing the system to hang; this issue was resolved. In addition, it was discovered that if `uart_wait_tx_idle_polling()` was not inserted immediately before entering sleep mode, the UART output buffer would be cut off midway, and this issue was also fixed.

Debugging was a tedious and grueling process, but it’s these kinds of fine-tuning details that determine the final stability.

## Creating a “Field-Based UI” Using PWAs and QR Codes

Finally, I added a little personal touch.

We've made the web app compatible with **PWAs (Progressive Web Apps)**. By including `manifest.json` and `sw.js` (Service Worker), users can install the app as an icon via the browser’s “Add to Home Screen” feature, and once cached, **it can be launched even without a signal**. Even if your phone loses signal in a remote mountain field, the app will still work just fine. After all, BLE operates independently of the smartphone’s cellular signal.

In addition, I created a **QR code label** (`docs/qr/print_label_ble.html`) to stick on the control box (Tupperware container) placed in the field. Just open it in a browser and print it, and you’ll get a beautiful, waterproof label. Scanning the QR code takes you to `https://amekusa03.github.io/LushGate/`, so anyone who visits (or even myself a few months from now) will understand how to use it just by looking at the label.

## The Evolution of the Design in a Nutshell

As of September 22, LushGate was one thing, but by September 29, it had become something almost entirely different.

I wrote about streamlining the power supply design (from solar to dry-cell batteries) in my previous post. This time, I’ll discuss streamlining the software side. By completely eliminating the Wi-Fi stack, web server, and HTML stored in flash memory—and delegating those roles to BLE and GitHub Pages—the firmware can now focus solely on its core functions: sensing, control, and low-power sleep mode.

The more you strip it down, the stronger it becomes. It seems the philosophy of subtraction isn't limited to hardware after all.
