# Summary of Design and Memory Management for Screen Inheritance and Multi-Level Inheritance in C# Windows Forms

2026-10-28 / C# / Windows Forms

## overview

This is a practical design pattern for C# Windows Forms that allows you to derive a form multiple times without breaking the design view and while preventing memory leaks and unnecessary resource consumption. The goal is to achieve a clean design that takes into account the post-compilation memory layout and reference topology (assembly structure).

---

## 1. Design Patterns for Event Triggers (Virtual Methods)
If you change automatically generated event handlers (such as `button1_Click`) to `protected` and reuse them in derived classes, it can lead to designer bugs and a breakdown of encapsulation. Best practice is to define **virtual methods (On...)** in the base class and have derived classes override them.

### Structural Diagram
* **Event Registration**: Call `+=` in the class that holds the control (typically the top-level parent).
* **Common Logic**: Written within the `protected virtual` method of the parent class.
* **Custom Logic**: Implemented in derived classes using `override`.

### Implementation Examples
```csharp
// --- 1. 基盤となる親フォーム（BaseForm） ---
public partial class BaseForm : Form
{
    public BaseForm()
    {
        InitializeComponent();
        // 親にある共通ボタンのクリックイベントを登録
        this.btnSubmit.Click += new EventHandler(BtnSubmit_Click);
    }

    // ハンドラ自体は private で外に見せない
    private void BtnSubmit_Click(object? sender, EventArgs e)
    {
        // 仮想メソッドを呼び出す（トリガ）
        OnSubmit(e);
    }

    // 派生クラスで書き換えるためのトリガメソッド
    protected virtual void OnSubmit(EventArgs e)
    {
        // 親クラスでの共通処理（バリデーションやログなど）
    }
}

// --- 2. 派生した子フォーム（ChildForm） ---
public partial class ChildForm : BaseForm
{
    protected override void OnSubmit(EventArgs e)
    {
        // 先に親の共通処理を動かす（順序は制御可能）
        base.OnSubmit(e); 

        // 子フォーム独自の固有処理
    }
}
```

## 2. Handling `sender` in Event Handlers
When triggering custom events or virtual methods from within a class, **the correct approach is to pass `this` to the `sender` argument**.

* **Reason for passing `this`**: 
  This is because, even if a class has been derived several times, the ``this`` in the code correctly points to the "last instance (entity) of the derived class" that is currently running.
* **The Meaning of `?` (Null-Allowed Type) in **`object? sender`**:**: 
  We have also accounted for the extremely rare cases—such as notifications from static classes—where `sender` is triggered by `null`, in order to conform to the common .NET-wide specification (signature). We’ve kept the entry point at `?` wide open, and when an exception is thrown, we pass `this`.

## 3. Lazy Initialization to Prevent Unnecessary Instance Creation (Memory Bloat)
It is a waste of resources to mark a heavy form—which may not be used in the constructor—with ``new`` just to suppress warnings related to C#'s "null-allowed reference types."

### Solution A: Use a null-allowed type (`?`) and generate it only when necessary
At first, it only consumes resources for variable declarations (including pointers), so it's extremely lightweight. It's well-suited for forms that are destroyed and recreated each time.
```csharp
private SubDetailForm? _detailForm;

private void BtnOpenDetail_Click(object sender, EventArgs e)
{
    if (_detailForm == null || _detailForm.IsDisposed)
    {
        _detailForm = new SubDetailForm();
    }
    _detailForm.Show();
}
```

### Solution B: Smart Lazy Initialization Using `Lazy__HTML_PH_0__`
No instance is created at the time the constructor is called; instead, the first time `.Value` is accessed, it is automatically converted to `new` behind the scenes.
```csharp
private readonly Lazy<SubDetailForm> _lazyDetailForm = new(() => new SubDetailForm());

private void BtnOpenDetail_Click(object sender, EventArgs e)
{
    // 初回アクセス時に生成、2回目以降は同じインスタンスを使い回す
    _lazyDetailForm.Value.Show();
}
```
> **Note**: By default, Windows Forms forms are set to `Dispose()` when closed (via the X button). Calling `_lazyDetailForm.Value.Show()` after the form has been destroyed will cause a crash at `ObjectDisposedException`. Therefore, if you intend to reuse the same instance, either hide it as `e.Cancel = true; this.Hide();` in the child form’s `FormClosing` event, or use the regeneration method based on the `IsDisposed` check in Solution A.

## 4. Measures to Prevent Memory Leaks Caused by Unregistered Events (Forgetting `-=`)
If a short-lived form uses ``+=`` to subscribe to events from long-lived external objects (such as static classes or singletons), a "memory leak" occurs in which the form remains in memory even after it is closed.

### Rules for References and Lifetimes
* **A long-lived (sender) event is subscribed to by a short-lived (receiver) (`+=`)** : ❌ **Dangerous (requires `-=`)**  
  (Because the issuer maintains a strong reference to the recipient, the form is not collected by the garbage collector even if it is closed.)
* **A short-lived (publisher) event is subscribed to by a long-lived (subscriber) (`+=`)** : ⭕️ **Safe (automatically cleaned up)**  
  (Since the event issuer disappears along with the short-lived instance when it is discarded, there is no risk of a leak.)

### Solution: Ensure that `Dispose` is properly disabled
If there are derived classes, override the base class’s `Dispose` method to unregister them all at once. Note that **registration using lambda expressions (anonymous functions) is prohibited for long-lived objects because unregistration via `-=` is difficult**.

```csharp
protected override void Dispose(bool disposing)
{
    if (disposing)
    {
        // フォームが破棄されるタイミングで確実に解除（-=）
        SharedService.DataChanged -= SharedService_DataChanged;
        components?.Dispose();
    }
    base.Dispose(disposing);
}
```

## 5. The Fundamental "Approach to Instances" and Screen Layout
The "main screen holds all ownership" topology discussed here is a very sound aggregation pattern.

```text
[メイン画面 (長生き)]
├──所有──> [メニュー画面] ➔ (イベント発火) ➔ メイン画面が += で受信（安全・リークなし）
└──所有──> [各小画面] ➔ メニューの選択に応じてメイン画面が生成・切り替え
```

### Points to Note When Switching Screens
If you discard an old small screen and create a new one using `new` each time, be sure to explicitly call **`.Close()` and `.Dispose()`** for the old small screen. If you fail to do this, even though the C# (managed) memory is released, the Windows display components (GDI objects/handles) will remain in the background, and the app will crash once the limit is reached.
