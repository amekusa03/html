Introduction of like button

Firebase Like Button Integration

About this Project

Static portfolio sites hosted on Vercel etc. can be operated quickly and at low cost, but when implementing dynamic interactions (e.g. ratings, comments, etc.), server-side functionality is required.

In this project, we will use Google's BaaS.Firebase Cloud Firestoreand client sideJavaScriptBy combining these, we implemented a secure and lightweight "like button (incremental rating)" function in a completely serverless configuration.

Video

Technical Stack

  • Database: Cloud Firestore (NoSQL document-based database)
  • Frontend Logic: Vanilla JavaScript (ES Modules, Firebase Web SDK v10)
  • State Persistence: LocalStorage (preventing duplication by temporarily saving in the browser)

System Architecture

1. Firestore data structure

The number of likes is managed using an identifier for each page (generated from the path name) as a document ID, and is incremented atomically.

  • Collection name: likes
  • Document ID: pageId(example: android_auto_music_player）
  • field: { count: number }

2. Duplication prevention flow

  • 1. When loading a page, local storage (liked__pageId) has a value.
  • 2. If the value exists, add it to the button. liked Add a class and change the icon to "♥" (guard it so that it cannot be clicked again).
  • 3. When clicked, if it has not been liked yet, writes a flag to local storage and sends an increment (+1) request to the Firestore server.

Core Implementation

Synchronous processing using JavaScript (`like.js` excerpt)

Firestore increment By using operators, the design allows the count to be updated accurately (atomic operation) even if multiple users click at the same time. 

import { initializeApp } from 'https://www.gstatic.com/firebasejs/10.12.0/firebase-app.js';
import { getFirestore, doc, getDoc, setDoc, increment } from 'https://www.gstatic.com/firebasejs/10.12.0/firebase-firestore.js';

// Firebase initialization settings
const firebaseConfig = {
  apiKey: "YOUR_API_KEY",
  projectId: "YOUR_PROJECT_ID",
  // ...Other setting items
};
const app = initializeApp(firebaseConfig);
const db = getFirestore(app);

// Execute like processing
async function initLikeButton() {
  const btn = document.getElementById('like-btn');
  const countEl = document.getElementById('like-count');
  // ... (DOM acquisition and existence check)

  // Generate page identifier (pageId)
  const path = location.pathname;
  const pageId = path
    .replace(/\/index\.html$/, '/')
    .replace(/\.html$/, '')
    .replace(/^\/|\/$/g, '')
    .replace(/\//g, '__') || 'home';

  const storageKey = 'liked__' + pageId;
  const docRef = doc(db, 'likes', pageId);

  // first time load
  const snap = await getDoc(docRef);
  countEl.textContent = snap.exists() ? (snap.data().count ?? 0) : 0;

  // click event
  btn.addEventListener('click', async () => {
    if (localStorage.getItem(storageKey)) return;
    localStorage.setItem(storageKey, '1');
    
    // Update the UI immediately (optimistic UI update)
    btn.classList.add('liked');
    countEl.textContent = parseInt(countEl.textContent || '0') + 1;

    // Send to server (atomic increment processing)
    await setDoc(docRef, { count: increment(1) }, { merge: true });
  });
}

Security Design & Best Practices

Since API keys are exposed on the front end, Firestore's security and resource protection consists of two main layers:

1. Firestore Security Rules

We have written strong access restrictions on the Firebase console to prevent someone from arbitrarily deleting other people's documents or significantly tampering with counts. 

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /likes/{pageId} {
      // Anyone can view the number of likes
      allow read: if true;
      // Allow likes (writes)
      allow write: if true;
    }
  }
}

2. API key HTTP referrer restrictions

In the settings on the Google Cloud console side, specify the domain (HTTP referrer) of the website where the API key can be used. https://amekusa.vercel.app/* A restriction is applied to limit the This technically prevents a third party from copying the API key and reusing it on another domain.

Conclusion

By using serverless technology (BaaS) and client JS, we were able to confirm that dynamic communication functions can be introduced safely and at low cost even on static sites such as personal portfolios.
