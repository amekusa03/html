C# Bug Report

About this Project

When an engineer with extensive C++ experience implemented C# properties, he misunderstood object reference control, resulting in a problem in which events were not notified (communications could not be received).

Patterns that occurred

Appearance class

  • FromMain:GUI main screen. Maintains a communication management instance.
  • FromEnv:GUI settings and communication test screen.
  • FromCommText:GUI text communication screen.
  • CommWifi:Wifi communication management. Sending is done by an asynchronous thread, and reception and abnormal occurrences are notified by events.

Workflow

  • 1. User starts FromMain
  • 2. FromMain generates CommWifi
  • 3. FromMain generates FromEnv
  • 4. FromMain passes CommWifi as constructor of FromEnv
  • 5. FromEnv subscribes to CommWifi reception/abnormal events
  • 6. User performs a communication test using FromEnv and confirms successful completion
  • 7. User closes FromEnv
  • 8. User opens FromCommText
  • 9. FromMain generates FromCommText
  • 10. FromMain passes CommWifi as constructor of FromCommText
  • 11. FromCommText subscribes to CommWifi reception/abnormal events
  • 12. User starts communicating with FromCommText
  • 13. Problem occurs: Sending is successful, but no event (reception notification) is received.

Root Cause: Incorrect Property Implementation

The code that caused the problem (simplified) is as follows. 

public CommWifi CommWifi
{
    get => new CommWifi(); // Generate a new instance on each access
}

Technical Background

The implementer may have written it with an image similar to C++'s "return entity (copy)", but In C# this is"Generate and return a new independent instance each time it is accessed"It becomes an action.

  • The `CommWifi` instance received by `FromEnv` and the instance received by `FromCommText` are different (different references).
  • It is also different from the source instance where `FromMain` actually performs communication processing.
  • As a result, even if you subscribe to events, you will be monitoring a location different from the instance that is actually running, and you will not receive notifications.

Conclusion

Although C# does not specify pointers, `class` always deals with references (like pointers). It is important for C++ engineers to understand that the class keyword is always synonymous with smart pointers.

Prevention and Review Guidelines

1. Implementing correct properties (using backing fields)

Return the same initialized instance to avoid unintentionally creating a new instance. 

private readonly CommWifi _commWifi = new CommWifi();
/// <summary>
/// Always return the same instance (reference)
/// </summary>
public CommWifi CommWifi => _commWifi;

2. Clearing events (memory leak prevention)

If old screen subscriptions remain after the screen is closed, it can cause unexpected behavior and memory leaks. 


// Example of cancellation in FromEnv
protected override void OnFormClosing(FormClosingEventArgs e)
{
    _commWifi.OnDataReceived -= HandleDataReceived; // Unsubscribe
    base.OnFormClosing(e);
}

3. Add to review checklist

  • Check property side effectsAre you using new in the :get accessor? (Avoid generating anything other than calculated properties)
  • Confirm identity:Do objects shared by multiple classes point to the same reference (`object.ReferenceEquals`) as intended?
  • life cycle management: Is the event registered with `+=` canceled with `-=` when the object is disposed (Dispose or Closing)?

Notes

If you feel that the app is running "somehow slow", If the behavior becomes unstable every time you open a particular screen, Careless instantiation (copy)Is it not being done? OrMultiple registration of eventsIf you suspect that something is occurring, This may also lead to early detection of defects.

Analysis

  • About the behavior when using C#'s automatically implemented property `public CommWifi CommWifi { get; } = new();`

    If the property implementation is "always new"

    In the code example of the problem, it is `get => new CommWifi();`, but if the implementation was as follows, a new instance would be generated every time it is accessed.

    A new instance is created each time it is accessed (an example that often causes bugs)

    
public CommWifi CommWifi => new CommWifi();

    This means that FromEnv and FromCommText are each operating on separate instances.

    Code improvement suggestions

    Prevent the recurrence of defects and create a safe C#-like design.

    
private readonly CommWifi _commWifi = new CommWifi();

// Always return the same instance (reference)
public CommWifi CommWifi => _commWifi;

  • About the IDisposable pattern and Weak Event pattern to prevent event handler release from being leaked

    Clearing events (preventing memory leaks and unexpected behavior)

    In the flow, after closing FromEnv, FromCommText is open. If you forget to release C# events, the instance will not be garbage collected (GC), causing memory leaks and unexpected behavior.

    
// Proper release in FromEnv
protected override void OnFormClosing(FormClosingEventArgs e)
{
    // FormEnv may remain in memory if you do not unsubscribe from the event
    _commWifi.OnDataReceived -= HandleDataReceived;
    base.OnFormClosing(e);
}

  • Code review checkpoints (additional proposal)

    In addition to "understanding copy," we recommend adding the following points to your checklist.

    Side effects on properties:

    Are you doing new inside the get accessor? (Avoid creating instances using other than calculated properties)

    Event lifecycle:

    Is the event registered with += canceled with -= when the object is disposed (Dispose or Closing)?

    Verifying identity:

    Do you have a habit of using object.ReferenceEquals(obj1, obj2) when debugging to make sure they are pointing to the same instance as you intended?

conclusion

C# hides pointers, but internally it handles "references (like pointers)". For C++ engineers: "The class keyword is always synonymous with pointers (smart pointers)"If you explain this, understanding often goes smoothly.

This case is a good example of how differences in language specifications distorted the design intent, and knowledge sharing is extremely valuable.
