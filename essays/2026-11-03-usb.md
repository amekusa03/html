# 光るLED、黙るPC 〜ESP32-S3とUSBケーブルの罠〜

2026-11-03

## 経緯

手のひらサイズでWi-FiもBluetoothも載り、おまけにネイティブUSBまで喋れるESP32。
最近はESP32-S3 Super MiniやC3 Super Miniのような超小型ボードが手頃に手に入るようになり、あれこれコードを書いて遊ぶにはもってこいの相棒だ。

先日までESP32-C3をいじっていたのだが、今度はESP32-S3を動かそうと思い立った。
さっそくPCから伸びるType-CケーブルをS3に挿し込む。
基板上の青いLEDがチカチカと元気に点滅を始めた。

……よし、通電は問題ない。プログラムを書き込もう。
そう意気込んでPCに向かったのだが、なぜか開発環境がポートを認識してくれない。

## 沈黙するPC

コンソールを開き、おなじみのコマンドを叩いてみる。

```bash
$ lsusb
Bus 001 Device 001: ID 1d6b:0002 Linux Foundation 2.0 root hub
Bus 001 Device 002: ID 0409:0059 NEC Corp. HighSpeed Hub
Bus 001 Device 003: ID 1ea7:0064 SHARKOON Technologies GmbH 2.4GHz Wireless mouse
Bus 001 Device 004: ID 045e:0737 Microsoft Corp. Optical Mouse
```

マウスとハブしか見当たらない。ESP32-S3の姿はどこにもない。
`dmesg -w` を眺めながらケーブルを抜き差ししてみても、ログはピクリとも流れない。
エラーログすら出ない完全な沈黙だ。

「さっきまでESP32-C3の書き込みに使っていたケーブルだし、断線のはずがない」

この確信が、見事なまでに判断を狂わせた。

## 外れた推理と悪戦苦闘

まず疑ったのは、ESP32お得意のブートモードだ。
「ファームウェアがおかしくなってUSBが死んでいるのかもしれない」と、米粒より小さいBOOTボタンをピンセットの先で押し込みながら挿し直してみる。しかし無反応。

次に疑ったのはLinuxのOS環境だ。
「Ubuntuのudevルールの権限不足か？」「カーネルのCDC-ACMドライバ周りか？」と設定をあれこれ見直してみる。
だが、そもそもカーネルがUSBデバイスの物理的な接続イベントすら検知していないのだから、ソフトや権限をいくらいじったところで意味がない。

目の前では、基板の青いLEDだけが相変わらず健気に光っている。
手も足も出ない。まさにあの「新品ESP32が沈黙した夜」の悪夢再びである。

## 決定打

「別のボードで動いたからケーブルは無実」という思い込みを一旦捨ててみることにした。
念のため、そのケーブルで手元のスマートフォンをPCに繋いでみる。

スマホの画面には「充電中」の表示が出た。
しかし、PC側で `lsusb` を叩いても、やはりデバイスは1台も増えない。

ここでようやく真相にたどり着いた。
**「このケーブル、給電線しか生きていない（データ線が繋がっていない）……！」**

## なぜ「C3は動いて、S3はダメ」だったのか？

疑問は残る。では、なぜさっきまでESP32-C3では普通に通信できていたのか。
調べていくうちに、格安超小型ボード特有の物理的事情が見えてきた。

1. **格安Type-Cコネクタの公差（ガタつき）**
   Super Miniなどの格安ボードはコネクタの寸法公差が甘い。ケーブル側のオスコネクタの微妙な長さやシェルの厚みで、「C3では奥まで届いてデータピンが接触していたが、S3のコネクタではわずかに届かず電源ピンしか接触していなかった」という物理的な接触不良が起きていたようだ。
2. **Type-Cの片面結線トラップ**
   安価なケーブルや基板には、片面のデータピン（D+/D-）しか配線されていないものがある。裏返して挿すと通信できる／できないという現象は、この界隈では日常茶飯事だ。
3. **内蔵USBコントローラのシビアさ**
   専用のシリアル変換チップ（CP2102やCH340など）に比べ、ESP32-S3の内蔵USB PHYは信号品質に敏感だ。低品質なケーブルだとノイズに負けてハンドシェイクに失敗することがある。

## 解決

引き出しの奥から、スマホ付属のしっかりしたデータ通信対応Type-Cケーブルを引っ張り出して繋ぎ直してみた。

```bash
$ lsusb
Bus 001 Device 014: ID 303a:1001 Espressif USB JTAG/serial debug unit
```

あっさり認識した。
`/dev/ttyACM0` にポートが生え、何事もなかったかのようにプログラムが書き込まれていく。
あの数時間の格闘は一体何だったのか。

## 教訓

- **`dmesg` に1ミリも反応がないときは、100%物理層（ケーブル・接触・電源）を疑うべし。**
- **「さっき別の機器で動いたケーブルだから」という油断が最大の罠。**
- **怪しいときはコネクタを180度裏返してみる、別の太い通信ケーブルに変えてみる。**

ソフトウェアの不具合やカーネル設定を疑う前に、まずは基本の「物理」を疑うこと。
オーディオの沼に続き、今度はUSBケーブルの沼に片足を突っ込んだ一日だった。
次はどんな沼が待っているのだろうか。
