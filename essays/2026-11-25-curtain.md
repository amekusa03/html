# 窓辺の知能とGoogle Home 〜ESP32-S3が先回りして教える「カーテンの閉め時」〜

2026-11-26

## 冷え切ってから閉めても、もう遅い

日本の住宅において、熱の最大の出入り口は言うまでもなく「窓」だ。

冬には部屋の暖気の約半分から6割が窓ガラスから逃げていき、夏には外の熱気の約7割が窓から容赦なく侵入してくる。高価な二重サッシや断熱リフォームに大金を投じずとも、「日差しがあるうちはカーテンを開けて太陽熱を取り込み、日が陰る直前にサッと閉めて空気の断熱層を作る」――理屈の上ではこれだけで、エアコンの効きも部屋の温もりも劇的に違ってくる。

……が、現実はそう思い通りにはいかない。

仕事や家事に追われているうちに外はすっかり薄暗くなり、ふと気づいたときには部屋が底冷えして、冷え切ったガラス窓からひたひたと冷気が降りてきている。「ああ、もっと早く閉めておけばよかった」と後悔する日々である。

もちろん、レールを自動で走る市販のカーテンロボットを導入する手もある。だが、あの独特のモーター音や、カーテンレールの継ぎ目に引っかかる小さなストレス、定期的なバッテリー充電の手間を考えると、機械任せで物理的に動かすこと自体が億劫に感じられてしまう。

「カーテンを無理にモーターで動かさなくても、家自身が外の光と風を感じ取って、ベストなタイミングで『そろそろ閉め時ですよ』と優しく声をかけてくれたらどうだろう？」

そんな思いつきから、切手サイズの超小型マイコン **ESP32-S3** とスマートスピーカー **Google Home** を直結する、自律型の温熱予測アナウンスシステムの工作が始まった。

## 今を見るのではなく「30分の傾き」から未来を読む

単に「外が暗くなったら知らせる」だけなら、センサーの値と数値を比べるだけの数行のコードで事足りる。しかし、それでは使い物にならない。頭上を一筋の雲が横切っただけでアナウンスが連呼されたり、西日が眩しく差し込んでいるのに判定が遅れたりするからだ。

そこでこのシステムの中核には、**「過去30分間の変化の傾き（スロープ）」から未来の熱移動を予測するロジック**を組み込んだ。

```mermaid
flowchart TD
    A[屋外センサーAPI] -->|5分おきに測定| B[リングバッファ (直近30分/6点)]
    B --> C[光量 & 外気温の「変化率（傾き）」算出]
    C --> D{季節・時刻・状態判定}
    D -->|冬の朝: 照度上昇| E[「冬・採光」カーテンを開ける]
    D -->|冬の夕: 照度急減| F[「冬・断熱」冷え込む前に閉める]
    D -->|夏の昼: 照度急増| G[「夏・遮熱」直射日光を遮断]
    D -->|夏の夜: 外気温低下| H[「夏・排熱」カーテンを開けて換気]
```

### 150 Luxの先にある「冷え込みの前兆」
実際に窓辺で外光を観察していると、「外の照度が150 Luxを下回り始めると、部屋の中が一気に薄暗くなる」という境界線が見えてきた。

冬期モードでは、この境界に向かって光量が急降下していく「傾き」をキャッチする。完全に日が沈んで部屋が冷え切ってからでは手遅れだ。**「これから冷え込むぞ」という予兆の段階で、「日が落ちて冷え込んできました。カーテンを閉めて暖気を逃がさないようにしましょう」と先回りして教えてくれる**ところに、この仕掛けの面白さがある。

### 一度言ったら黙る「引き算の知性」
家族と暮らすリビングにおいて、一番敬遠されるのは「おしゃべりすぎる機械」だ。

一度アナウンスしたら最低1時間は再通知しないクールダウンタイマーを設け、現在の開閉状態を記憶して開いている時に「開けろ」と重複して言わないようにした。もちろん夜間（22:00〜7:00）は完全に沈黙する。この「出しゃばりすぎない引き算の設計」があってこそ、日常の風景に自然と溶け込んでくれる。

## サーバーレスの意地：ESP32単体でGoogle Castを直撃する

Google Home（Nest Hub）に好きな音声を喋らせようとするとき、世のスマートホーム開発者の多くはRaspberry Piや常時起動のPC、あるいはHome Assistantといった中継サーバーを立てる道を選ぶ。Google Cast（CastV2）プロトコルはProtocol Buffers（Protobuf）によるバイナリ構造で、TLSの暗号化ハンドシェイクやセッション管理が必要なため、マイコン単体で扱うには仕様があまりに重たく複雑だからだ。

だが、私は常時動かすシステムのために余計な中継サーバーを増やしたくなかった。

目指したのは、**親指サイズのESP32-S3単体から、家庭内LANにあるGoogle Home（ポート8009）へ直接TLS接続し、CastV2メッセージを直接叩き込む**というピュアな実装だ。

### バイナリの深淵：消えた「transportId」の謎
開発中、最大の壁となったのがGoogle Homeが返す起動応答（`RECEIVER_STATUS`）のパケット処理だった。

TLS接続を確立し、標準メディアプレイヤー（AppId: `CC1AD845`）の起動要求（`LAUNCH`）を投げるところまではすんなり進んだ。ところが、Google Homeから戻ってくる応答の中に確かに存在するはずの通信ID（`transportId`）を、プログラムがどうしても拾えず、タイムアウトを繰り返してしまったのだ。

数時間頭を抱えた末に行き着いた原因は、CastV2のバイナリフレーミングという極めて初歩的な罠だった。

CastV2通信では、全パケットの先頭に「4バイトのビッグエンディアン整数」としてデータ長がくっついてくる。約900バイトの応答パケットの場合、先頭バイト列は `0x00 0x00 0x03 0x8A ...` と並ぶ。

ここでC言語でおなじみの文字列探索関数 `strstr()` を使ってしまっていたのが運の尽きだった。先頭の `0x00` は、文字列の世界では終端を表すヌル文字（`\0`）だ。関数は先頭を見た瞬間に「長さゼロの空文字列だな」と判断し、探索を即座に諦めていたのである。

```text
[ 受信バイナリの先頭データ ]
00 00 03 8A 08 00 12 08 ... "transportId":"f63960a3-..."
 ↑
 従来の strstr() はここでヌル文字 '\0' と誤認して即座に探索終了していた！
```

`memcmp` を使ったバイナリセーフな探索処理に書き直した瞬間、シリアルモニタに鮮やかなログが流れた。

```text
I (9577) CAST_CLIENT: Successfully extracted transportId: f63960a3-557a-4e66-9a29-c1b68ef0e06e
I (9616) CAST_CLIENT: Cast LOAD request sent for: http://192.168.11.22/test.mp3
```

その直後、リビングのGoogle Nest Hubの画面がパッと切り替わり、澄んだ日本語のアナウンスがスピーカーから鳴り響いた。PCもラズパイも挟まず、小さなマイコンチップが自力でGoogleのスピーカーを鳴らした瞬間である。この手応えがあるから、電子工作はやめられない。

## 手元の管制塔と、年間50円の常時起動

「今、何が起きているか」が手元で見えると、自作デバイスへの愛着は一気に跳ね上がる。

ESP32-S3の内部で軽量なWebサーバーを走らせ、スマホやPCのブラウザから直接叩けるダッシュボードを用意した。

```text
+--------------------------------------------------------------+
| 🏠 カーテン開閉予測システム                                    |
| 現在ステータス: [カーテン: 閉] [照度: 0.1 lx] [外気: 8.8 ℃]   |
+--------------------------------------------------------------+
| 📢 アナウンス履歴 (最新20件)                                  |
| 2026/11/24 23:15 | 冬・断熱（閉） | 外気:8.8℃/照度:0.1lx | [成功] |
+--------------------------------------------------------------+
| [ Google Home でテスト音声を再生 ]                           |
+--------------------------------------------------------------+
```

現在のカーテン推定状態や外気温、過去のアナウンス履歴が並び、画面からワンタップで音声テストもできる。10秒ごとの自動更新で、部屋にいながら「今、家が何を考えているのか」が手に取るように伝わってくる。

### スリープさせないという贅沢
乾電池駆動のIoTならDeep Sleepで限界まで眠らせるのが鉄則だが、このシステムはあえて**「常時起動」**を選んだ。

実測してみると、Wi-Fiに常時つながっていても消費電力はわずか0.2W（5Vで30〜50mA程度）。年間365日つけっぱなしにしたところで、電気代は**約50円**そこそこだ。スリープからの復帰待ち時間（数秒のWi-Fi再接続ラグ）が一切なく、ブラウザを開けばゼロ秒で画面が表示され、キャスト要求も即座に飛ぶ。この快適さは、常時給電ならではの特権と言える。

### おまけ：消えない青色LEDと遮光テープ
ちなみに、開発の終盤でひとつクスッと笑える出来事があった。ボード上の青色LEDがどうしても消灯できないのだ。

コードをいくら見直しても、GPIOをLOWにしてもHIGHにしても点滅が止まらない。調べてみると、使っていた「ESP32-S3 SuperMini」という互換ボードのハードウェア仕様だった。この青色LEDはマイコンの足ではなく、基板上のバッテリー充電管理ICに直結していたのだ。USB給電だけだと、充電ICが「電池はどこだ？」と探すパルスを出し続けるため、どうしても点滅してしまうらしい。

ソフトウェアの理屈が通用しないハードの素朴さに苦笑しつつ、黒い遮光テープを小さく切ってペタッと貼る。こんな泥臭いオチも含めて、DIYの楽しい思い出である。

## 窓辺から世界へ：自サイト「雨草の庭」とのリアルタイム連携

家の中のローカルネットワークで完結して動くシステムは確かに堅牢で愛着が湧く。しかし、運用を続けていると新たな欲が出てくる。「いま外出先だけど、部屋のカーテンは閉まっただろうか？」「外気と室温の差はどれくらい開いているだろうか？」

そこで、このESP32-S3に**自作Webサイト（雨草の庭）へ環境データを直接レポーティングする機能**を増設することにした。

仕組みは極めてシンプルかつモダンだ。ESP32-S3が5分ごとのセンサー取得時、あるいはカーテン・換気のアナウンスが発火した瞬間に、本サイトが稼働しているVercelのサーバーレスAPI（`/api/curtain`）へHTTPS POSTで最新状態を送り込む。

```json
{
  "timestamp": 1795691603,
  "outdoor_temp": 11.4,
  "indoor_temp": 27.0,
  "lux": 0.1,
  "curtain_state": "CLOSED",
  "last_action": "冬・断熱（閉）",
  "action_time": "2026-11-26 17:15"
}
```

暗号化されたHTTPS通信をマイコンで行うため、ESP-IDF標準の証明書バンドル（`esp_crt_bundle`）を組み込み、Let's Encrypt等の公式ルート証明書を安全に検証しながら直結させている。サーバー側はVercel KV（Redis）の `SET curtain:latest` にデータを保持し、サイトを訪れたブラウザからのGETリクエストに対して即座に応答する。

### 部屋の息遣いが滲み出るWebサイト
この連携によって、本サイト「雨草の庭」のサイドバーに**「居室・温熱観測」**という小さなリアルタイムウィジェットが加わった。

ブラウザを開くと、現在の室温や外気、照度とともに、「カーテン: 閉」「冬・断熱（閉）」といった我が家の窓辺の動態が、緑色の稼働ランプとともに静かに表示される。

単なるテキストと写真を並べた静的な個人サイトが、自分の暮らす物理空間と一本の細い通信ラインでつながり、部屋の呼吸や温度がそのままWebの片隅に息づいている。外出先からスマホでサイトを開き、「ああ、夕暮れの冷え込みに合わせてカーテンを閉めてくれたな」と確認できるときの小さな高揚感は、IoT工作冥利に尽きる。

## 機械に動かされるのではなく、そっと促される心地よさ

カーテンをモーターで無理やり自動開閉するのではなく、光の移ろいを感じ取った家が、そっと住人に声をかける。

声をかけられた人間は、ふと窓の外の空を見上げ、季節の移り変わりを感じながら、自分の手で静かにカーテンを引く。

テクノロジーが人間の生活を機械的に代行するのではなく、**人間の心地よい行動をそっと後押ししてくれる関係（アンビエント・コンピューティング）**。

窓辺の小さなESP32-S3とGoogle Homeが織りなすこの仕掛けは、便利さの先にある「人と家とのちょうどいい距離感」を、静かに教えてくれている気がする。
