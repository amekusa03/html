# ESP-IDFの潮目をみる 〜 v6への進化と、あえて今とどまる選択 〜

2026-11-16

## ふと気になった「今のバージョン」

ESP32-C3と温湿度センサー（SHT30/31）、そしてSwitchBot APIを組み合わせて自作したエアコン自動制御システム。久しぶりにプロジェクトを開いたとき、ふと「そういえば、今使っているESP-IDFのバージョンはいくつだろう？」と気になった。

PlatformIOのビルド構成を確認してみると、現在動いている環境は **ESP-IDF `v5.5.4`**（GCC 14.2.0）だった。

そこで現在の最新動向を調べてみると、本家Espressifからはすでにメジャーアップデートを経た **`v6.1`** がリリースされており、PlatformIOの `platform-espressif32` も最新版の **v8.0.0** で `framework = espidf` における v6.1 対応を果たしていた。

「せっかくだから最新版に上げてみようか」と思いかけたのだが、v6系の新機能と変更点を読み進めていくうちに、今回はあえてバージョンアップを見送り、現行環境を維持することにした。

## 次世代を見据えたESP-IDF v6の進化

メジャーバージョンアップとなるv6系（v6.0 / v6.1）には、今後の組み込み開発を見据えた魅力的な改善がいくつも盛り込まれている。

- **標準Cライブラリが `Picolibc` へ移行**: 長年使われてきた `Newlib` に代わり、組み込み向けに最適化された軽量な `Picolibc` が標準となった。Flash使用量やヒープ割り当て、`printf` などのI/O処理時のスタック消費量が抑えられるのは嬉しい進化だ。
- **ツールチェーンと開発環境の刷新**: コンパイラが **GCC 15.1.0** へ引き上げられ、クロスプラットフォームのインストーラ **EIM (ESP-IDF Installation Manager)** も導入された。
- **新世代チップへの本格対応**: 2.4GHz/5GHzデュアルバンドWi-Fi 6に対応した **ESP32-C5** や **ESP32-C61** が正式サポートとなり、新しいラインナップへの道筋が整えられている。

これから新規に書き始めるプロジェクトであれば、ぜひ試してみたい内容だ。ただ、すでに稼働している既存プロジェクトを移行するとなると、少し事情が変わってくる。

## 設計の近代化と、手元のコードへの影響

移行ガイドに目を通してみると、v5.x から v6系へのアップデートは、長年の歴史の中で積み重なった古い仕様を整理し、フレームワーク全体をモダンに再設計する大きな節目であることがわかる。

まず影響を受けるのが、暗号化まわりの刷新だ。
セキュリティ基盤が **Mbed TLS v4.0** へ更新されたことに伴い、暗号化処理が標準規格である **PSA Crypto API** へと一本化された。これまで馴染み深かった `mbedtls_sha*` や `mbedtls_md*` といった従来の関数群は役目を終え、整理されている。

実は、これが自作のエアコン制御システムにとって一番の書き換えポイントだった。
SwitchBot API v1.1 ではリクエストヘッダに付与する署名（`sign`）を **HMAC-SHA256** で生成する必要があり、`main.cpp` の中でまさに `mbedtls/md.h` を直接呼び出して実装していたのである。

```cpp
// main.cpp 内の SwitchBot API v1.1 署名生成コード（ESP-IDF v5.x）
mbedtls_md_context_t ctx;
mbedtls_md_type_t md_type = MBEDTLS_MD_SHA256;

mbedtls_md_init(&ctx);
mbedtls_md_setup(&ctx, mbedtls_md_info_from_type(md_type), 1);
mbedtls_md_hmac_starts(&ctx, (const unsigned char *)secret.c_str(), secret.length());
mbedtls_md_hmac_update(&ctx, (const unsigned char *)data.c_str(), data.length());
mbedtls_md_hmac_finish(&ctx, hmacResult);
mbedtls_md_free(&ctx);
```

v6系へ移行するなら、この部分も `psa_crypto_init()` や `psa_mac_compute()` を使った新しい作法へと書き直すことになる。

また、周辺機器ドライバやコンポーネント構成もすっきりと整理された。
v5.x 時代に非推奨（Deprecated）となっていた旧ドライバ群（旧ADC、I2S、RMT、タイマーグループなど）は新しい `esp_driver_*` 体系へと完全にバトンタッチされ、`cJSON` などの一部機能もコアから切り離されて ESP Component Registry 経由で必要なものだけを導入するモジュール構成へと進化している。

フレームワークとしては実に理にかなったスリム化なのだが、手元のコードや外部ライブラリが旧来のAPIを前提にしている場合、周辺ライブラリ側の対応が一巡するまでは慎重に歩調を合わせる必要がありそうだ。

## Arduino Core が「v5.5系」を選んでいる安心感

もう一つ参考になったのが、PlatformIO の最新プラットフォーム（`platform-espressif32 v8.0.0`）におけるフレームワークごとのベースバージョンの違いだ。

- **`framework = espidf`** を選んだ場合：最新の **ESP-IDF `v6.1`**
- **`framework = arduino`** を選んだ場合：最新の Arduino Core `v3.3.12` でも、内部ベースは **ESP-IDF `v5.5.5`**

膨大な数のセンサーライブラリや通信ライブラリを支える Arduino エコシステムにおいても、まずは互換性と安定性を重視し、成熟した v5.5 系をベースに据えていることが窺える。

## 「枯れた安定版」を見極めるのも楽しみのうち

新しいバージョンが出るとつい追いかけたくなるが、日常の裏方で黙々と動く家電制御のような仕組みでは、「今動いているものが、明日も変わらず静かに動き続けること」が何よりありがたい。

現在使っている **ESP-IDF `v5.5.4`** は、機能的にも十分新しく、周辺のライブラリ資産とも気持ちよく噛み合うバランスの良い世代だ。長期サポート（LTS）として2028年頃までメンテナンスが続くこともあり、既存のシステムを任せるにはこれ以上ない環境と言える。

新しいv6系はこれから新しく組む実験プロジェクトで楽しむことにして、部屋のエアコンを見守るこのシステムには、もうしばらく慣れ親しんだv5.5系で頑張ってもらおうと思う。こうした「技術の潮目」を眺めて立ち止まる時間も、個人開発ならではの穏やかな楽しみだ。
