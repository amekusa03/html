# C# Windows Forms 画面継承・多段階継承における設計とメモリ管理まとめ

2026-10-28 / C# / Windows Forms

## 概要

C#のWindows Formsで画面（Form）を何回か派生させる際に、デザイン画面を破壊せず、メモリリークや無駄なリソース消費を防ぐための実践的な設計パターンです。コンパイル後のメモリ配置や参照のトポロジー（アセンブル構造）を意識した綺麗な設計を目指します。

---

## 1. イベントトリガ（仮想メソッド）の設計パターン
自動生成されるイベントハンドラ（`button1_Click` 等）を `protected` にして派生先で使い回すと、デザイナーのバグやカプセル化の崩壊を招きます。基底クラスに**仮想メソッド（On...）**を用意し、派生先でオーバーライドするのがベストプラクティスです。

### 構造イメージ
* **イベントの登録**: コントロールを持つクラス（主に最上位の親）で `+=` する。
* **共通ロジック**: 親クラスの `protected virtual` メソッド内に記述。
* **固有ロジック**: 派生クラスで `override` して記述。

### 実装例
```csharp
// --- 1. 基盤となる親フォーム（BaseForm） ---
public partial class BaseForm : Form
{
    public BaseForm()
    {
        InitializeComponent();
        // 親にある共通ボタンのクリックイベントを登録
        this.btnSubmit.Click += new EventHandler(BtnSubmit_Click);
    }

    // ハンドラ自体は private で外に見せない
    private void BtnSubmit_Click(object? sender, EventArgs e)
    {
        // 仮想メソッドを呼び出す（トリガ）
        OnSubmit(e);
    }

    // 派生クラスで書き換えるためのトリガメソッド
    protected virtual void OnSubmit(EventArgs e)
    {
        // 親クラスでの共通処理（バリデーションやログなど）
    }
}

// --- 2. 派生した子フォーム（ChildForm） ---
public partial class ChildForm : BaseForm
{
    protected override void OnSubmit(EventArgs e)
    {
        // 先に親の共通処理を動かす（順序は制御可能）
        base.OnSubmit(e); 

        // 子フォーム独自の固有処理
    }
}
```

## 2. イベントハンドラにおける `sender` の扱い
カスタムイベントや仮想メソッドをクラス内部から発火させる場合、`sender` 引数には **`this` を渡すのが正解**です。

* **`this` を渡す理由**: 
  何代か派生したクラスであっても、コード上の `this` は現在動いている「一番末尾の派生クラスのインスタンス（実体）」を正しく指し示すため。
* **`object? sender` の `?`（Null許容型）の意味**: 
  静的クラスからの通知など、極稀に `sender` が `null` で発火される例外的なケースも想定した.NET全体の共通仕様（シグネチャ）に合わせるため。受ける窓口は `?` で広く開け、発火時は `this` を渡します。

## 3. 無駄なインスタンス生成（メモリ肥大化）を防ぐ遅延初期化
C#の「Null許容参照型」による警告を消すためだけに、コンストラクタで使わない可能性のある重いフォームを `new` してしまうのはリソースの無駄です。

### 対策A：Null許容型（`?`）にして必要な時だけ生成
最初は変数宣言（ポインタ分）だけの消費なので超軽量です。都度破棄・再生成するフォームに適しています。
```csharp
private SubDetailForm? _detailForm;

private void BtnOpenDetail_Click(object sender, EventArgs e)
{
    if (_detailForm == null || _detailForm.IsDisposed)
    {
        _detailForm = new SubDetailForm();
    }
    _detailForm.Show();
}
```

### 対策B：`Lazy<T>` を使ったスマートな遅延初期化
コンストラクタ時点では実体は生成されず、`.Value` に初めてアクセスした瞬間に裏側で自動的に `new` されます。
```csharp
private readonly Lazy<SubDetailForm> _lazyDetailForm = new(() => new SubDetailForm());

private void BtnOpenDetail_Click(object sender, EventArgs e)
{
    // 初回アクセス時に生成、2回目以降は同じインスタンスを使い回す
    _lazyDetailForm.Value.Show();
}
```
> **注意**: Windows Formsのフォームは、閉じる（×ボタン）とデフォルトで `Dispose()` されます。破棄後に `_lazyDetailForm.Value.Show()` を呼ぶと `ObjectDisposedException` でクラッシュするため、同一インスタンスを使い回す場合は子フォーム側の `FormClosing` イベントで `e.Cancel = true; this.Hide();` として非表示にするか、対策Aの `IsDisposed` 判定による再生成を採用してください。

## 4. イベントの未解除（`-=` 忘れ）によるメモリリーク対策
外部の長生きするオブジェクト（staticクラスやシングルトン等）のイベントを、寿命の短いフォームが `+=` で購読すると、フォームを閉じてもメモリに残る「メモリリーク」が発生します。

### 参照と寿命のルール
* **長生き（発行側）のイベントを、短生き（受信側）が購読（`+=`）** : ❌ **危険（要 `-=`）**  
  （発行元が受信側への強い参照を掴み続けるため、フォームを閉じてもGC回収されません）
* **短生き（発行側）のイベントを、長生き（受信側）が購読（`+=`）** : ⭕️ **安全（自動回収される）**  
  （短生き側の破棄とともにイベント発行元ごと消えるため、リークしません）

### 対策：`Dispose` での確実な解除
派生クラスがある場合は、基底クラスの `Dispose` メソッドをオーバーライドして一括解除します。なお、**ラムダ式（匿名関数）での登録は `-=` での解除が困難なため、長生きするオブジェクトに対しては禁止**です。

```csharp
protected override void Dispose(bool disposing)
{
    if (disposing)
    {
        // フォームが破棄されるタイミングで確実に解除（-=）
        SharedService.DataChanged -= SharedService_DataChanged;
        components?.Dispose();
    }
    base.Dispose(disposing);
}
```

## 5. 本質的な「インスタンスの持ち方」と画面構成
今回の「メイン画面がすべての所有権を握る」トポロジーは非常に健全な集約パターンです。

```text
[メイン画面 (長生き)]
├──所有──> [メニュー画面] ➔ (イベント発火) ➔ メイン画面が += で受信（安全・リークなし）
└──所有──> [各小画面] ➔ メニューの選択に応じてメイン画面が生成・切り替え
```

### 画面切り替え時の注意点
古い小画面を捨てて新しい小画面を毎回 `new` する場合、古い小画面に対して必ず **`.Close()` および `.Dispose()`** を明示的に呼び出してください。これを怠ると、C#のメモリ（マネージド）は解放されても、Windowsの画面部品（GDIオブジェクト/ハンドル）が裏で残り続け、上限に達した時点でアプリがクラッシュします。
