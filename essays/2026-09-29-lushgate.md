# 畑の自動散水機、Wi-FiからBLEへ ── ルーターなしで畑からスマホに繋がる

2026-09-29 / ESP32 / IoT / BLE

前回のエッセイでは、ソーラー発電という大艦巨砲から単三電池4本＋単一電池2本という質素な布陣への「引き算」について書いた。ハードウェアの設計がひとまず固まったところで、次の課題がのしかかってきた。

「どうやってスマホから設定を変えるか」

問題の本質はシンプルだ。畑は家の裏にあり、Wi-Fiルーターの電波が届くかどうかも怪しい。届いたとしても、ESP32をAP（アクセスポイント）モードで動かす場合、スマホをESP32のSSIDに繋ぎ直す必要がある。日常使いのWi-Fiから手動で切り替えて、ブラウザでIPアドレスを直打ち──これが面倒くさいのだ。「IoT」を名乗っておきながら、接続のたびに設定画面とにらめっこするのは本末転倒である。

## Deep SleepからLight Sleepへ：最初の大きな変更

9月22日時点の設計では、測定の合間に ESP32 を **Deep Sleep** させる想定だった。Deep Sleep は RAM の内容をすべて捨て、RTC メモリだけを残して眠る最深スリープだ。電力的には最高だが、「起きるたびにリセットと同じ」という性質がある。

ところが実装を進めるうちに、Deep Sleep との相性が悪い部分が浮かび上がってきた。

Deep Sleep からの復帰はリセットと同義なので、RAM 上の変数（雨量積算値など）が吹き飛ぶ。RTC スローメモリ（`RTC_DATA_ATTR`）に退避するにしても、容量が限られており、設定構造体まで全部乗せるのは窮屈だ。何より、後述する BLE スタック（NimBLE）が Deep Sleep とまともに共存できない。BLE は起動時に大量の初期化処理を走らせるため、3分ごとに初期化→終了→初期化を繰り返すと処理時間が膨らみ、消費電力の節約どころではなくなる。

そこで採用したのが **Light Sleep（浅い睡眠）** だ。RAM の内容がそのまま保持され、タイマーやGPIO割り込みで瞬時に目が覚める。消費電流は約 **0.13mA** と Deep Sleep（0.006mA）には劣るが、3分周期の間欠動作では1日の総消費電流はわずかに増えるだけ。乾電池の持ちに実害が出るレベルではない。

状態変数を `RTC_DATA_ATTR` で装飾する必要もなくなり、ふつうの `static` 変数として宣言するだけでよくなった。コードがぐっとシンプルになる。

## Wi-Fi AP モードの廃止とBLEへの全面移行

Light Sleep への切り替えに伴い、通信方式も根本から見直した。

9月23日のコミット（`feat: complete software implementation`）の時点では、まだ Wi-Fi AP モードが残っていた。ESP32 がアクセスポイントになり、スマホを繋いで `192.168.4.1` にアクセスする旧来の方式だ。設定画面のHTMLをフラッシュ上に埋め込み、Web サーバー（`web_server.c`）と Wi-Fi AP 初期化（`wifi_ap.c`）を動かしていた。

そして9月29日、`feat: migrate to NimBLE Web Bluetooth` というコミット一発で、この構成が丸ごと入れ替わった。

削除されたファイル: `web_server.c`、`wifi_ap.c`、`web_server.h`、`wifi_ap.h`、そして内蔵WebページのHTMLファイル。  
追加されたファイル: `ble_gatt.c`、`ble_gatt.h`、そして `docs/index.html`（GitHub Pages 上の Web Bluetooth アプリ）。

Wi-Fi スタックをまるごと捨て、**NimBLE**（ESP-IDF 内蔵の軽量BLEスタック）に乗り換えた。スマホとの通信は **Web Bluetooth API** を使い、ブラウザから直接 BLE デバイスに繋ぐ。スマホのWi-Fi設定を触る必要はゼロ。ルーターも不要。

操作の流れはこうなった。

1. ESP32 の **BOOTボタン（GPIO9）** を押す（LEDが点滅してアドバタイジング開始）
2. スマホのブラウザで `https://amekusa03.github.io/LushGate/` を開く
3. 「**LushGate に接続**」をタップ → BLE接続確立
4. 散水スケジュール・雨量閾値・ポンプ秒数を変更、時刻同期、手動散水テスト、履歴閲覧

Wi-Fi より圧倒的に手軽だ。何より、Web アプリを GitHub Pages でホストすることで、ファームウェアの中からHTMLを排除できた。ファームウェアはファームウェアの仕事だけをすればいい。

## BLE GATT の設計：5本のキャラクタリスティック

`ble_gatt.c` の中身は、NimBLE の GATT サービスとして定義された5本のキャラクタリスティックで構成されている。

| キャラクタリスティック | 役割 |
|---|---|
| `CONFIG` (0001) | 設定値の読み書き・NVS保存 |
| `TIMESYNC` (0002) | スマホ時刻をEpochでRTCに書き込み |
| `PUMP_CMD` (0003) | ポンプON/OFF・秒数指定 |
| `STATUS` (0004) | 雨量・ポンプ状態・センサー生値のJSON通知 |
| `HISTORY` (0005) | 過去60回の散水履歴をインデックス指定で取得 |

`STATUS` キャラクタリスティックは Notify（push通知）に対応しており、接続中は1秒ごとにリアルタイムでセンサー値が飛んでくる。雨滴センサーの電圧がジリジリと上下するのをスマホ画面で眺めながら、指先に水滴を乗せてテストする──なかなか楽しい体験だった。

## 二重散水バグとの格闘

BLE の実装が一段落した直後に、やっかいなバグが顔を出した。

「リセット直後に、本来やるべきでない散水が走る」

原因を掘り下げると、こういうことだった。Light Sleep からの復帰と、電源断後のリセットが、ファームウェアから見て区別しづらい状況があった。「本日散水済み」を示すフラグ（`s_last_water_day`）は RAM に持っているから Light Sleep 後は生きているが、電池交換などで完全リセットがかかると、当然 RAM が消えてフラグも 0xFF に戻る。NVS（不揮発ストレージ）に保存した前回散水時刻と照合すれば防げるはずが、リストア処理の順序が甘く、「20時間ガード」が機能しないケースがあった。

`fix: prevent multiple waterings using RTC slow memory and pre-watering state commit` というコミットで、散水実行の**直前**に「本日散水済みフラグ」と「散水時刻Epoch」を NVS に書き込む順序保証を入れた。万が一散水中にリセットがかかっても、次回起動時に「あ、今日はもう散水したな」と正しく判断できるようにした。

さらに同日の `fix(firmware): Light Sleep復帰の安定化` コミットでは、BLE モード終了時に NimBLE の `deinit` を明示的に呼ばないとモデムと Light Sleep が競合してハングすることが判明し、対処した。加えて、スリープ直前に `uart_wait_tx_idle_polling()` を挟まないと UART の出力バッファが途中で切れることも分かり、こちらも修正した。

デバッグは地味で泥臭かったが、こういう細部の詰めが最終的な安定性を決める。

## PWAとQRコードで「畑に貼るUI」を作る

最後に、ちょっとしたこだわりを入れた。

Web アプリを **PWA（Progressive Web App）** に対応させた。`manifest.json` と `sw.js`（Service Worker）を添えることで、ブラウザの「ホーム画面に追加」からアプリアイコンとしてインストールでき、一度キャッシュすれば**圏外でも起動できる**。山奥の畑でスマホが圏外になっても、アプリ側は問題ない。BLE はスマホの電波と無関係に動くのだから。

さらに、畑に置いた制御ボックス（タッパー）に貼るための **QRコードラベル**を `docs/qr/print_label_ble.html` として作った。ブラウザで開いて印刷するだけで、防水シール用の美しいラベルが刷れる。QRコードを読み込めば `https://amekusa03.github.io/LushGate/` に飛ぶから、訪れた人（もしくは数ヶ月後の自分）がラベルを見ただけで使い方が分かる。

## 設計の変遷をひとことで

9月22日時点の LushGate と、9月29日の LushGate は、ほぼ別物になった。

電源設計（ソーラー→乾電池）の引き算は前回書いた。今回はソフトウェア側の引き算だ。Wi-Fi スタック、Webサーバー、フラッシュ内蔵HTML──これらをまるごと捨て、BLE と GitHub Pages に役割を委ねることで、ファームウェアは本来のセンシング・制御・省電力スリープだけに集中できるようになった。

削れば削るほど、強くなる。引き算の哲学は、ハードウェアだけじゃなかったようだ。
