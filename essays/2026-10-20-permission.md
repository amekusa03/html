# AIに「読めません」と言われた話 〜Ubuntuでアクセス権限の沼にハマる〜

2026-10-20

## 気がつけば

エッセイの誤字脱字チェックをAIに手伝ってもらおうと、ファイルを読み込ませていたところ、
ところが返ってきたのは、こんなエラーだった。

```
Permission denied for read_file(/media/data/Users/ame/document/homepage/amekusa/essays/2026-10-20-specker.md). Matches default system policy.
```

自分のファイルなのに、「読めません」と言われてしまった。

## 最初の推理

ファイルのパーミッションに問題はない。ワークスペースを信頼する設定も済ませてある。それでも拒否される。

怪しいのは、パスの中の `/media` だった。
ドキュメントフォルダは、実際には別のディスクにあり、ホームからはシンボリックリンクでつながっている。

```
/home/kusa/ドキュメント -> /media/data/Users/ame/document
```

AIが見ているのはリンクを展開した実パスで、その先が `/media` 以下だ。「`/media` はリムーバブルメディア扱いでブロックされているのでは？」と考えた。

## 外れた推理

そこで、ディスクを `/data` にも bind マウントし、リンクの向き先を張り替えた。

```
/home/kusa/ドキュメント -> /data/Users/ame/document
```

結果は、やはり拒否。エラーのパスが `/data/...` に変わっただけだった。
`/media` が原因という推理は、見事に外れた。

## 本当の原因

エラーをよく読むと、「default system policy」に一致した、とある。
ワークスペースとして登録されているのは `/home/kusa/ドキュメント/...` で、AIが判定に使う実パスは `/data/...`。両者が一致しないため、範囲外とみなされていたようだ。

ワークスペースを開き直したところ、あっさり読めるようになった。
ただし、これも状況からの推測にすぎない。内部の判定ロジックを確認したわけではない。

## 学んだこと

- シンボリックリンクの先は、実パスで判定されることがある。
- 原因を決めつけて環境を変える前に、エラーメッセージを読み直すほうがいい。
- 結局、最初にワークスペースを開き直していれば、手間は省けたかもしれない。

ちなみに、シェル経由ならアクセスできる状態だった。だが、ポリシーを迂回するのは気持ちが悪いので、使わなかった。
音の沼に続いて、今度はパスの沼にハマってしまったようだ。
